# ADR：NetMedic Next 架构决策与迁移路线

- **状态**：提案（Proposed），尚未批准进入实现阶段
- **日期**：2026-10-10
- **适用仓库**：wudicyg/netmedic
- **当前稳定基线**：NetMedic 1.5.1
- **决策主题**：独立 C# 桌面应用 vs. 保留 PowerShell 后端的混合架构

## 1. 摘要与建议决策

**建议采用混合架构作为 NetMedic Next 的过渡与首选方案：C# 负责桌面 UI、任务编排、统一领域模型、策略与结果呈现；现有 PowerShell 5.1 能力先通过受限适配层复用；新增能力优先以清晰接口实现，并根据测试结果决定是否用 C# / Windows API 替换具体模块。**

这不是永久绑定 PowerShell 的决定，而是一条可逆的迁移路径。先提取现有行为契约和测试，再让 C# 成为新产品的主要应用层，最后按模块迁移后端。不要把“全面翻译脚本”作为目标；目标是提高诊断覆盖率、故障归因质量、修复成功率和可验证性。

建议保持两个产品轨道：

1. **NetMedic 1.x**：稳定维护，继续修复缺陷、保护 Safe Repair、维持现有发布流程；不把 Next 的实验性架构直接塞进稳定主线。
2. **NetMedic Next**：独立应用与模块化引擎，先进行架构验证，再逐步迁移功能；不要求首个原型就覆盖 1.x 全部能力。

本 ADR 本身不批准任何网络修改行为，也不构成发布或版本号提升的理由。

## 2. 当前基线与约束

当前仓库是 PowerShell 项目，正式发布版本为 1.5.1。入口为 NetworkRepair.ps1，模块主要位于 src/，自动化测试位于 tests/NetworkRepair.Tests.ps1，发布包与只读验证工具位于 tools/，CI 覆盖 Windows PowerShell 5.1 和 PowerShell 7 的语法/测试路径。

已存在的资产包括：

- Safe Repair 的历史网络 Profile 候选识别、安全门槛与修复计划。
- DNS、DHCP、IP、默认网关、适配器、Connection Profile 和 NCSI 相关诊断。
- 备份、恢复点、恢复校验与失败回滚路径。
- 按需刷新 NlaSvc / netprofm 的服务刷新策略。
- WinForms GUI、CLI/TUI、JSON 报告、脱敏诊断包、发布打包和更新检查。
- Pester 测试及 Windows 10 + PowerShell 5.1 的核心行为验证。

当前 Deep Repair 的范围仍较窄：它在现有 Profile 处理基础上清理 NetworkList\NewNetworks；这不等于全面的 Windows 网络协议栈恢复。Windows 11、更多系统语言和网卡/VPN/虚拟网络组合仍需要扩展验证。

### 必须保持的约束

1. **Safe Repair 不回退**：现有已验证安全门槛与回归测试作为迁移基线。
2. **先诊断、再计划、后执行、最后验证**：UI 不直接执行系统修改命令。
3. **最小权限**：只读诊断尽可能不提权；只有需要写入的动作才进入受控提权路径。
4. **不把备份夸大为万能回滚**：每种动作必须声明真实可恢复范围；不可逆或无法可靠回滚的动作必须明确告知。
5. **不执行无依据的“万能重置”**：每个动作需要证据、前置条件、风险说明、超时和验证标准。
6. **不把敏感诊断数据默认上传**：本地报告、脱敏导出与任何未来联网功能分开设计。
7. **不为了架构改造而无意义发版**：只有功能增量与验证证据达到发布门槛时才更新版本。

## 3. 决策驱动因素

NetMedic Next 的目标不是多调用几个 Windows 命令，而是建立完整的故障处理闭环：

1. 发现网络异常并识别检测覆盖范围；
2. 基于多项证据判断候选根因，并允许返回“未知/证据不足”；
3. 生成可解释、可预览、有风险等级的修复计划；
4. 按依赖顺序执行动作，支持超时、取消、状态反馈与失败分支；
5. 每步或每组动作后重新验证；
6. 只在明确安全边界内尝试恢复，并记录未恢复或部分恢复状态；
7. 将真实 Windows 场景固化为可重复测试。

衡量成功的指标应是场景覆盖、判断质量、修复前后变化与失败保护，而不是脚本行数、命令数量或语言迁移比例。

## 4. 架构选项比较

评分：1 = 弱，5 = 强。分数是基于当前仓库与项目目标的工程判断，不是性能基准测试。

| 维度 | 全 C# 原生重写 | C# + PowerShell 混合迁移 | 仅继续扩展 PowerShell |
|---|---:|---:|---:|
| 首个可用原型速度 | 2 | 4 | 5 |
| 复用现有已验证行为 | 2 | 5 | 5 |
| 长期 UI 与任务编排能力 | 5 | 4 | 2–3 |
| 对 Windows API 的直接控制 | 5 | 4 | 3–4 |
| 当前维护者迁移成本 | 2 | 4 | 5 |
| 逐步替换单个模块的能力 | 3 | 5 | 3 |
| 脚本运行时与部署复杂度 | 5 | 3 | 4 |
| 统一类型、契约与编译期检查 | 5 | 4 | 2–3 |
| 当前总体风险 | 2 | 4 | 4（短期）/ 2–3（长期） |

### 选项 A：独立 C# 桌面应用，后端全部原生实现

**优点**

- UI、并发、取消、状态机和错误模型可以在统一的 .NET 类型体系内设计。
- 可直接使用受支持的 Windows API、系统管理接口及 .NET 测试工具。
- 发布产物不必依赖外部 PowerShell 脚本执行环境；具体部署仍需处理运行时与 Windows API 兼容性。
- 更适合长期维护的大型桌面应用和强类型领域模型。

**缺点与风险**

- 需要重建当前诊断、备份、恢复、服务刷新、报告和打包流程。
- 原生重写容易在细节上偏离已验证的 PowerShell 行为，特别是注册表边界、服务依赖和失败回滚。
- 首个版本交付时间更长，功能迁移与真实 Windows 验证可能互相阻塞。
- 语言更换不会自动提高诊断准确率，也不会自动使系统修改更安全。

**适用时机**：已有稳定领域契约、足够的回归测试和明确的 Windows API 方案后，可按模块原生化；不建议第一步就一次性全量重写。

### 选项 B：C# 桌面应用 + 受限 PowerShell 后端（推荐）

**优点**

- 可尽快建立新 UI、领域模型、任务编排和统一结果展示，同时复用成熟的 1.x 行为。
- 可逐步替换模块；每次迁移只需证明新实现符合相同契约与验收矩阵。
- 能把旧脚本限制在明确的兼容边界内，不让 GUI 与 PowerShell 代码继续深度耦合。
- 可以将“迁移是否值得”变成每个模块的独立决策，而不是一次性押注。

**缺点与风险**

- 需要同时管理 C# 与 PowerShell 两种运行环境、错误模型、序列化和进程生命周期。
- 子进程启动、标准输出/错误输出、编码、超时、取消和提权边界必须明确。
- 若允许任意脚本文本或自由参数透传，混合层可能扩大命令注入和权限滥用风险。

**必要的控制措施**

- 不允许 UI 拼接或执行任意 PowerShell 字符串。
- 后端只暴露固定动作名和版本化输入/输出契约；参数必须做类型、范围和枚举验证。
- 通过 JSON 或等价的结构化协议传递数据，日志与机器可读结果分离。
- 设置超时、退出码、取消语义、标准输出/错误输出上限和进程清理规则。
- 高权限写操作必须经过动作级策略检查；只读诊断尽可能在普通权限下执行。
- 进程通信失败时，默认状态应为“失败且未确认发生了什么”，不能推断操作未执行，也不能盲目重试非幂等动作。

### 选项 C：继续只用 PowerShell + WinForms

**优点**：迁移成本最低，现有工具链与发布流程可继续使用，适合继续维护 1.x、补充诊断和验证现有小范围功能。

**缺点**：当界面变为多步骤向导、复杂任务队列、可取消动作和跨模块状态流时，维护成本可能上升。脚本、UI、进程全局状态之间需要持续保持纪律；对下一代产品而言，继续增加脚本函数可能延迟建立稳定的领域模型与模块契约。

**适用时机**：短期继续维护 1.x；不建议把它作为 Next 长期唯一架构。

## 5. 目标架构

建议采用分层结构，依赖从 UI 指向应用服务，再指向领域契约与适配器。核心策略层不直接调用 Windows 命令。

    NetMedic Next
    ├── Desktop UI (C# / WPF)
    │   ├── 诊断总览与详细证据
    │   ├── 修复计划预览 / 风险确认
    │   ├── 任务进度、取消与结果
    │   └── 恢复点 / 日志 / 脱敏报告
    ├── Application Layer
    │   ├── Diagnostic Orchestrator
    │   ├── Repair Planner / Policy Engine
    │   ├── Repair Workflow / State Machine
    │   ├── Verification Orchestrator
    │   └── Report & Privacy Service
    ├── Domain Contracts
    │   ├── Finding / Evidence / Confidence
    │   ├── RepairAction / Risk / Preconditions
    │   ├── ExecutionResult / VerificationResult
    │   └── BackupScope / RecoveryCapability
    ├── Adapters
    │   ├── PowerShell 5.1 Adapter (transition)
    │   ├── Native Windows Adapter (C# / Windows APIs)
    │   └── Read-only system probes
    └── Privileged Execution Boundary
        ├── Action allowlist
        ├── Elevated operation broker (only if required)
        ├── Audit log / timeout / cancellation
        └── Recovery and failure-state reporting

### 5.1 桌面层

建议原型采用 C# 与 WPF，原因是目标平台为 Windows，且需要丰富的桌面交互。UI 仅呈现状态和收集用户确认，不直接执行命令、修改注册表或重启服务。

UI 必须能够展示当前结论及可信度、关键证据与检测失败项、将执行的每个动作及影响范围、是否需要管理员权限/断网窗口/重启、每个动作的执行结果和修复后验证结果，以及“已恢复”“部分恢复”“未恢复”“无法判断”等不同终态。

### 5.2 领域模型

建议统一以下概念：

- **Finding**：诊断发现；包含稳定代码、严重程度、证据、可信度和局限。
- **Evidence**：具体观测值、来源、采集时间、是否成功采集。敏感字段必须标注数据分类。
- **RepairAction**：固定动作标识、版本、前置条件、风险等级、影响范围、是否需要提权/确认/重启、是否可恢复。
- **RepairPlan**：由 Finding 和策略产生的有序动作列表，包含不执行原因和用户可读说明。
- **ExecutionResult**：开始/结束时间、退出状态、变更摘要、错误分类、是否可能已发生部分变更。
- **VerificationResult**：按动作定义的验证项、修复前后差异、是否达到目标，以及未通过原因。
- **RecoveryCapability**：声明能恢复的具体范围和限制；不可恢复的动作不得伪装成完全可回滚。

诊断结论应允许“正常”“异常”“未知”“检测受限”。例如 DNS 探测失败不能单独证明 DNS 配置错误；NCSI 失败也可能与门户认证、代理或策略相关。决策引擎必须使用组合证据和显式置信度，而不是把某个布尔值直接映射为根因。

### 5.3 PowerShell 适配器契约

过渡期 PowerShell 后端只负责既有或暂未迁移的 Windows 交互。C# 应调用已发布的固定入口和动作，不应通过字符串拼接生成脚本。

协议至少包含：

- protocolVersion
- requestId
- actionId（固定白名单）
- arguments（按动作 schema 验证）
- timeoutSeconds
- correlationId

响应至少包含：

- protocolVersion、requestId
- status（Succeeded / Failed / TimedOut / Cancelled / Partial / Unknown）
- result（结构化业务数据）
- errorCode、safeMessage
- startedAt、finishedAt
- changeSummary、verification

协议版本不兼容时应拒绝执行。stdout 用于机器可读协议时不得混入普通日志；诊断日志应走独立通道或单独文件。任何写操作都必须在调用前完成动作级授权、参数验证和风险确认。

**不要**为了方便而建立“以管理员身份执行任意 PowerShell”的通用服务。若后续引入常驻高权限服务，需要单独的安全 ADR、威胁建模和签名/部署设计。

## 6. 模块边界与责任

| 模块 | 主要责任 | 初始实现建议 | 不应承担的责任 |
|---|---|---|---|
| Desktop UI | 呈现诊断、计划、进度、结果 | C# / WPF | 直接运行命令或决定根因 |
| Diagnostic Contracts | 统一 Finding/Evidence 结构 | C# 类型与 JSON schema | 执行系统探测 |
| Diagnostic Orchestrator | 安排只读探测、汇总失败 | C# | 直接修改网络 |
| Windows Network Probes | 网卡、IP、路由、DNS、代理、服务、NCSI 等观测 | 先复用已验证逻辑；逐模块迁移 | 自动决定高风险修复 |
| Root Cause / Policy Engine | 组合证据、置信度、排除规则、候选根因 | 纯函数 C#，数据驱动规则 | 运行系统命令 |
| Repair Planner | 生成有序计划、风险和前置条件 | 纯函数 C# | 跳过确认直接执行 |
| Repair Executor | 执行固定 RepairAction、限时、取消、审计 | C# 编排 + 受限适配器 | 接受任意命令文本 |
| Backup / Recovery | 记录动作前状态、声明恢复范围、恢复与验证 | 按动作逐项实现 | 承诺超出能力的完全回滚 |
| Verification | 对照目标重新检测并判断是否恢复 | 独立模块 | 只以命令退出码作为成功 |
| Privacy / Reporting | 脱敏、本地报告、导出 | 复用现有脱敏规则并增加测试 | 默认上传原始诊断数据 |
| PowerShell Adapter | 过渡期调用既有脚本功能 | PowerShell 5.1 | 成为新的业务策略中心 |
| Native Windows Adapter | 对已迁移动作使用 API/受支持接口 | C# / Windows API | 无证据扩大修改范围 |
| Packaging / Update | 构建、签名、哈希、升级与回滚 | 独立发布工程 | 与诊断逻辑耦合 |

## 7. 功能迁移顺序

迁移应按风险和可验证性排序，而不是按文件顺序翻译。

### Phase 0 — 基线冻结与行为契约

**目标**：把现有可用行为变成可重复验收的契约。

- 记录 1.5.1 基线、现有 CLI/JSON 输出、Safe Repair 候选规则、备份/恢复范围与服务刷新结果。
- 将诊断故障场景整理为测试矩阵：健康网络、无网卡链路、DHCP、静态地址、DNS、代理、VPN/虚拟网卡、NCSI 受限、权限不足、服务缺失。
- 为敏感数据字段分类；明确哪些只用于本机内部报告，哪些可进入脱敏包。
- 为所有修复动作建立前置条件、风险、变更范围、验证与恢复说明。
- 修正验证盲区后再把测试矩阵作为 Next 的迁移基准。

**退出条件**：每项现有安全行为有自动化回归测试；关键恢复范围有明确声明；不以文档或静态源码字符串断言代替关键行为测试。

### Phase 1 — 纯 C# 领域模型与诊断模拟器

**目标**：先建立引擎骨架，不接触真实系统。

- 创建 Finding、Evidence、RepairAction、Plan、ExecutionResult、VerificationResult 类型。
- 实现纯函数策略规则，输入模拟诊断结果，输出稳定的诊断分类和计划。
- 为低可信度、证据冲突、探测失败等情况定义“未知/不自动修复”策略。
- 加入 JSON schema 或等价版本化序列化契约。

**退出条件**：CI 中对模拟场景运行单元测试；相同输入产生确定性结果；未知字段/协议版本按约定安全失败。

### Phase 2 — 桌面原型 + 只读诊断

**目标**：建立 Next 的可见体验，不修改系统。

- 实现 C# / WPF 首屏、诊断详情、证据查看和导出。
- 先通过受限适配器复用当前 PowerShell 只读诊断，或实现独立只读 probe。
- 显示诊断覆盖情况与失败项；避免将未采集到的数据显示成“正常”。
- 所有报告默认本地保存；分享前显式选择脱敏导出。

**退出条件**：普通用户权限下可完成只读诊断；适配器超时、异常退出、编码错误、无网络与权限不足均有明确状态；诊断不会执行写操作。

### Phase 3 — 修复计划与 Safe Repair 兼容

**目标**：迁移决策与计划，不扩大修改范围。

- 将当前 Safe Repair 规则映射到统一的 RepairAction。
- 计划预览与执行必须使用同一个不可变计划对象或同一份序列化计划。
- 通过适配器调用现有 Safe Repair 时，先比较新旧计划的动作集合和保护对象。
- 备份、恢复、活动 Profile 与 Managed Profile 安全门槛作为硬性回归项。

**退出条件**：新旧计划在既定场景下完全一致；Windows 实机验证通过；不存在新的自动删除路径；旧 1.x 仍可独立发布与运行。

### Phase 4 — 低影响网络修复动作

**目标**：从一个动作开始，验证端到端闭环。

推荐按单动作逐步引入，例如 DNS 缓存清理；随后才考虑在确认接口使用 DHCP 且证据支持时，对指定接口续租。每个动作应包含前置条件、幂等性说明、超时、执行后探测、失败处理和用户提示。

**退出条件**：模拟测试与 Windows 实机测试均通过；验证结果能区分“动作成功”与“问题已解决”；动作失败或部分成功不会触发盲目重试。

### Phase 5 — 深度修复模块

**目标**：以证据驱动增加代理、网络服务、Winsock/TCP/IP 等诊断与恢复能力。

- 先做只读诊断与证据积累，再逐个引入写操作。
- 代理修复必须区分 WinHTTP、用户代理、系统/企业策略与应用私有代理；未能判断时只提示，不清空。
- Winsock/TCP/IP 重置等动作属于高影响操作，需要单独确认、重启说明和恢复能力声明。
- Windows 系统“网络重置”作为最后手段和明确的人工选择，不作为自动修复链默认动作。
- 不要把清理 NetworkList\NewNetworks 当成网络协议栈修复的替代品。

**退出条件**：每种高影响动作有独立的安全审查、失败场景测试、可恢复范围说明与真实 Windows 证据；默认策略不会在证据不足时执行。

### Phase 6 — 原生化与移除旧后端

**目标**：按实际收益逐模块替换 PowerShell。

每个模块满足以下条件后才可原生迁移：行为契约稳定、测试覆盖充分、Windows API 路径清楚、混合调用的维护成本确实高于原生实现。迁移期间保留对照测试，确保新实现与原适配器在规定场景下输出一致。

**退出条件**：模块在 Windows 10/11 和目标环境矩阵通过；关键场景不再依赖 PowerShell；删除适配器后发布包、故障报告和恢复路径仍然完整。

## 8. 测试策略与合并门槛

测试分层执行。CI 中不应对运行中的开发者或 CI 主机执行真实网络重置、注册表破坏或服务停启。

### Gate A — 静态与契约检查（每个 PR）

- C# 构建、格式和分析器通过。
- PowerShell 5.1 与 PowerShell 7 对仍保留的脚本运行语法/兼容性检查。
- JSON/schema 协议兼容性测试通过。
- 关键安全策略不得依赖 UI 隐藏按钮来实现；必须在执行边界再次验证。
- 依赖与打包清单可复现，无不必要的权限或网络访问。

### Gate B — 单元与故障注入（每个 PR）

- 诊断策略、计划生成、风险门槛、状态机和脱敏逻辑用纯数据测试。
- 覆盖空数据、部分探测失败、证据冲突、异常字段、超时、取消、重复请求和适配器异常退出。
- 对危险动作验证：未确认、前置条件不满足、目标接口不明确、参数非法时必须拒绝。
- 用 mock/fake adapter 验证执行器；CI 不运行真实写操作。

### Gate C — 集成测试（每个 PR 或专门流水线）

- 在隔离测试进程中验证 C# ↔ PowerShell 结构化协议、退出码、编码、stderr、超时和进程清理。
- 使用只读适配器验证真实系统探测。
- 以模拟注册表/服务适配器验证计划和失败分支。
- 测试日志不混入 JSON、敏感字段不进入默认输出。

### Gate D — Windows 实机验收（发布候选前）

至少覆盖 Windows 10 与 Windows 11 的目标支持版本、实际采用的运行时、DHCP 与静态 IPv4、IPv6、Wi-Fi 与 Ethernet、VPN/虚拟网卡/多网卡、企业代理或策略环境、中文与英文系统、普通用户只读诊断、管理员写操作、权限不足和 UAC 取消、网络中断、探测超时、服务不可用、修复后未恢复与恢复失败。

高影响修复必须在可恢复的虚拟机或专用测试机中测试，保留修复前快照和证据；不得在日常生产设备上做破坏性验证。

### Gate E — 发布包与升级/回滚验收

- 安装/便携包内容、数字签名（如采用）、哈希和版本信息一致。
- 干净环境启动、缺少依赖、被安全软件拦截、更新失败和恢复到上一版本均有明确结果。
- GUI 自检不会弹出阻塞窗口；崩溃日志不包含不必要的敏感数据。
- 发布正文、变更记录、支持矩阵与实际测试证据一致。

### 必须满足的硬性门槛

1. **Safe Repair 回归为零**：不得删除当前活动 Profile 或 Managed Profile。
2. **没有未声明的写入**：只读诊断不得更改网络设置、注册表或服务状态。
3. **无证据不执行高影响动作**：不满足前置条件时拒绝执行。
4. **不把执行成功等同于修复成功**：必须进行独立验证。
5. **部分失败可见**：执行结果必须能表达 Partial / Unknown，不可将不确定状态伪装为成功。
6. **可恢复能力真实**：恢复测试必须验证目标范围，而不是只检查命令退出码。
7. **隐私门槛**：脱敏报告通过负向测试，确保机器名、MAC、IP、NetworkId、注册表路径和凭据不会意外泄漏。
8. **兼容性声明有证据**：未测平台不得宣传为已完全支持。

## 9. 仓库与分支策略

### 9.1 当前仓库

继续将 wudicyg/netmedic 作为 1.x 稳定维护仓库：

- main 只接收通过 PR 与 CI 的变更。
- 保留现有发布脚本、1.x 标签、CHANGELOG 与发布验证文档。
- 只合并与 1.x 稳定性相关的修复；Next 的架构实验不直接混入主线。
- 不为新增 ADR 或单纯目录整理提升应用版本号。
- 后续若有必要，可以在原仓库增加明确标记为 1.x 的安全修复与兼容性补丁。

### 9.2 Next 的代码仓库

**建议在架构原型通过前先不要创建正式新仓库。** 先在单独分支或独立原型目录中验证以下内容：C# UI 构建、PowerShell 适配器协议、只读诊断端到端流程、CI 与发布包可行性。原型一旦证明架构可行，再创建独立仓库（暂定名称可为 netmedic-next，名称尚未注册或确认），避免过早分叉并重复维护。

如果选择立即建立独立仓库，则它必须有自己的版本、CI、依赖锁定、支持矩阵、威胁模型和发布流程；不得直接复用 1.x 的版本号与发布标签。

### 9.3 PR 纪律

- 每个 PR 聚焦一个架构边界或一个可验收能力。
- 先合并文档和纯模型，再合并只读诊断，最后才是写操作。
- 不把“架构已完成”作为一次性大 PR；每阶段都要有可运行成果。
- 不自动合并依赖高影响行为的 PR。
- 不创建 Release，直到对应功能的 Gate A–E 达到其适用门槛。

## 10. 风险登记表

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 新旧行为不一致 | 原安全保证回退 | 基线测试、对照计划、逐模块迁移 |
| PowerShell 进程/协议失败 | 结果未知、重复执行风险 | request ID、超时、部分/未知状态、非幂等动作禁止盲目重试 |
| 管理员执行边界过宽 | 权限滥用或命令注入 | 固定动作白名单、强类型参数、最小权限、独立安全审查 |
| 诊断过度推断根因 | 错误修复或扩大故障 | 多证据规则、置信度、未知状态、人工确认 |
| “回滚”被过度承诺 | 系统配置无法完全恢复 | 每动作声明恢复范围、实机故障注入 |
| 多平台支持声明超前 | 用户环境故障 | 支持矩阵与实测证据绑定 |
| 两套产品重复维护 | 开发精力分散 | 1.x 只维护稳定性；Next 采用阶段门槛与独立路线图 |
| 过早创建新仓库 | CI、文档与发布流程重复 | 先做小型端到端原型，达到退出条件再分仓 |

## 11. 决策与未决事项

### 本提案建议批准的决策

- Next 采用 **C# 桌面应用 + 受限 PowerShell 适配器** 作为初始架构。
- C# 承担 UI、领域模型、策略、任务编排和验证流程；PowerShell 仅作为过渡后端，不成为新的业务策略中心。
- Safe Repair 的现有行为与测试作为不可回退的基线。
- 先完成只读诊断原型，再引入低风险修复，最后逐项审查高影响恢复。
- Next 初期不直接合并到 1.x 的 main；新仓库在原型通过后再创建。
- 所有高影响操作必须独立验收，不能因为已有管理员权限或注册表备份就默认安全。

### 需要在实现前确定的事项

1. Next 的目标 Windows 最低版本和具体支持矩阵。
2. 目标 .NET 版本、部署模式（自包含或依赖安装运行时）及签名策略。
3. 是否需要单独的提权执行进程；在完成威胁建模前，不建设常驻高权限服务。
4. PowerShell 适配器是调用现有入口还是提供独立的受限 worker；最终协议需通过安全审查。
5. 新仓库命名、许可证、贡献流程和发布签名方案。

这些事项不妨碍开始 Phase 0 和 Phase 1，但在引入真实写操作前必须明确。
